I added a worker-side token bucket (Redis) so a task only calls the model if tokens are available, otherwise it gets delayed and retried later. Multimodal Foundation Models & Embeddings

PinClip

image encoder

  • CNN Stem
  • Funnel ViT

text encoder

  • SigLIP
  • descriptive text: The sparkling glitter adds a touch of glamour to any outfit…
  • keyword text: men shoes/streetwear/sneaker，更像是一个search query
  • 不是把两种text拼接在一起,因为太长影响效果

Fusion encoder

  1. 把image和text token拼接起来，得到[I1, I2, …, T1, T2, …], 维度[N, d], N=Nv + Nt
  2. 过 2 层 Transformer, 得到Z_j，维度[N, d]
  3. cross attention
    • r_j = MHA(q, Z_j, Z_j), [1, d]
    • q:[1,d]
  4. L2 normalization

Image-to-text Alignment

  • 每个 image-text pair 单独做 binary classification,每一个pair只有两个取值，match/unmatch
  • L_I2T = L_desc + L_key
  • I → image encoder → image embedding
  • T_desc → text encoder → desc text embedding
  • T_key → text encoder → keyword text embedding
  • 用sigmoid loss, BCE-with-logits
    • 正样本 loss = -log(sigmoid(score))
    • 负样本 loss = -log(1 - sigmoid(score))

Pin-to-Pin alignment

  • image tokens + descriptive text tokens经过Fusion Encoder，得到fused Pin embedding M’_j
  • 也是BCE，score = t * (u_i · v_j) - c
    • t: temperature, 属于[-1, 1]，作用是把 similarity 的差异放大或缩小
    • c: bias，决定 similarity 要高到什么程度，模型才认为这对 pair 是正样本。需要bias是因为 contrastive learning 里负样本远多于正样本
    • u_i，v_j：同一个batch中每个pin的fused embedding
  • random walk：从一个 query Pin 出发，在图上随机走，走很多次之后，看哪些 Pin 被访问得最多。
  • For each query Pin, sample N = 5 positive Pins。离线计算每个 query Pin 的 top 50 neighbor candidates，训练时sample N = 5. 最后有2.4 billion Pin pairs

MRL

L_total = L_I2T(full 256d) + L_P2P(full 256d)

nums = [10,9,2,5,3,7,101,18]
import bisect
def sol(nums):
    g=[]
    g_idx=[]
    n=len(nums)
    parent=[-1]*n #记录nums[i]在最终答案里的上一个数字的index
    for i, x in enumerate(nums):
        idx=bisect.bisect_left(g, x)
        if idx>0:
            # its has a preceding number
            parent[i]=g_idx[idx-1]
        if idx<len(g):
            g[idx]=x
            g_idx[idx]=i
        else:
            g.append(x)
            g_idx.append(i)
    cur_idx=g_idx[-1]
    res=[]
    while cur_idx!=-1:
        res.append(nums[cur_idx])
        cur_idx=parent[cur_idx]
    return res[::-1]

消息可靠性

生产者->MQ

  • 生产者开启 confirm 模式
    1
2
3
4
5

    channel.confirmSelect(); // 开启Confirm模式
channel.basicPublish(exchange, routingKey, MessageProperties.PERSISTENT_TEXT_PLAIN, message.getBytes());
if (!channel.waitForConfirms(5000)) {
    // 消息未确认，重试或记录日志
}
  • 异步确认：发送消息后不阻塞等待 MQ 的 ACK，而是通过回调函数接收 ACK 通知；若回调中发现未确认（如 ACK 失败、超时），将未确认的消息存入本地缓存，定期触发重试，直到收到 ACK 或达到最大重试次数；
  • 同步确认：发送消息后阻塞等待 ACK

MQ

  1. 持久化（必做）：设置消息和队列为「持久化模式」（RocketMQ 默认开启），MQ 会将消息和队列信息写入磁盘，即使 MQ 进程宕机、重启，也能从磁盘恢复消息，避免内存中的消息丢失；
  2. 集群多副本（进阶，提升可靠性）：搭建 RocketMQ 集群，配置多副本（类似镜像队列），将队列数据同步到集群多个节点，设置节点同步模式（如同步复制）；

MQ->消费者

  1. 手动 ACK
    • 自动 ACK 的确定：会存在消费者收到，确认之后没消费，消费者挂了，数据丢失
  2. 死信队列： 当消息多次重试（如3次）仍处理失败（如系统异常），将消息转入「死信队列」，由人工介入排查处理，避免消息无限重试或被丢弃

幂等性

为什么会有重复的消息

  1. 生产者没收到 MQ 的 ACK，又发了一次
  2. MQ 没收到消费者的 ACK，又发了一次

解决

  • 数据库唯一索引
  • Redis SETNX /Lua 脚本查状态改状态

对比Kafka的优势

  1. Consumer 端自带重试机制，当消费消息失败时，RocketMQ 会自动将消息放入重试队列。
  2. 当消费消息失败时，RocketMQ 会自动将消息放入重试队列

Multimodal Foundation Models & Embeddings

PinClip

image encoder

  • CNN Stem
  • Funnel ViT

text encoder

  • SigLIP
  • descriptive text: The sparkling glitter adds a touch of glamour to any outfit…
  • keyword text: men shoes/streetwear/sneaker，更像是一个search query
  • 不是把两种text拼接在一起,因为太长影响效果

Fusion encoder

  1. 把image和text token拼接起来，得到[I1, I2, …, T1, T2, …], 维度[N, d], N=Nv + Nt
  2. 过 2 层 Transformer, 得到Z_j，维度[N, d]
  3. cross attention
    • r_j = MHA(q, Z_j, Z_j), [1, d]
    • q:[1,d]
  4. L2 normalization

Image-to-text Alignment

  • 每个 image-text pair 单独做 binary classification,每一个pair只有两个取值，match/unmatch
  • L_I2T = L_desc + L_key
  • I → image encoder → image embedding
  • T_desc → text encoder → desc text embedding
  • T_key → text encoder → keyword text embedding
  • 用sigmoid loss, BCE-with-logits
    • 正样本 loss = -log(sigmoid(score))
    • 负样本 loss = -log(1 - sigmoid(score))

Pin-to-Pin alignment

  • image tokens + descriptive text tokens经过Fusion Encoder，得到fused Pin embedding M’_j
  • 也是BCE，score = t * (u_i · v_j) - c
    • t: temperature, 属于[-1, 1]，作用是把 similarity 的差异放大或缩小
    • c: bias，决定 similarity 要高到什么程度，模型才认为这对 pair 是正样本。需要bias是因为 contrastive learning 里负样本远多于正样本
    • u_i，v_j：同一个batch中每个pin的fused embedding
  • random walk：从一个 query Pin 出发，在图上随机走，走很多次之后，看哪些 Pin 被访问得最多。
  • For each query Pin, sample N = 5 positive Pins。离线计算每个 query Pin 的 top 50 neighbor candidates，训练时sample N = 5. 最后有2.4 billion Pin pairs

Dynamo

virtual nodes

  • compared to basic consistent hashing, each node is assigned to multiple points on the ring

  • advantages

    • If a node becomes unavailable, the load handled by this node is evenly dispersed across the remaining available nodes.
    • When a new node is added to the system, the new node accepts a roughly equivalent amount of load from each of the other available nodes.
    • The number of virtual nodes that a node is responsible for can be decided based on its capacity, accounting for heterogeneity in the physical infrastructure.

  • solved consistent hashing’s problems

文件系统

inode

每个文件都有唯一的 inode, 只在当前文件系统唯一

存放的信息有

  • 文件权限（File Permissions）：读（r=read）、写（w=write）、执行（x=execute），示例：rw-r–r–（所有者可读可写，所属组和其他用户仅可读）
  • 文件所有者和所属组（File Owner & Group）：
    • 所有者 UID（User ID）
    • 所属组 GID（Group ID）
  • 文件大小（File Size）：单位字节（Byte），区分普通文件（存储内容大小）和目录文件（存储目录项的大小）
  • 时间戳（Timestamps）：3 个核心时间属性
    • ctime（Change Time）：inode 元数据修改时间（如权限、所有者变更）
    • mtime（Modify Time）：文件内容修改时间
    • atime（Access Time）：文件内容最后访问时间
  • 数据块指针（Data Block Pointers）：最核心字段，直接或间接指向存储文件内容的数据块物理地址
  • 链接数（Link Count）：指向该 inode 的硬链接数量，默认新建文件时 link count = 1

读写分离&分表分库

发表于： 2025-12-17 分类于： MySQL

读写分离

常见架构

  • 一主多从
  • 主主互备 + 多从：两个主库互为主从，解决主库单点故障，读请求仍走从库

实现

  • 在业务和数据库之间加一层代理（MySQL Router），由它把读写请求分发给不同节点
  • 第三方组件（sharding-jdbc）

分库分表

  • 单表的数据达到千万级别以上->分表
  • 单库的 CPU/IO/ 连接数达到上限->分库

路由规则

  • 哈希路由（取模）
  • 范围路由 （user_id 1100 万→库 0，101200 万→库 1）
  • 一致性哈希（把 key 和节点映射到同一个哈希环上，key 顺时针找到第一个节点作为归属节点）

数据迁移

  • 停机迁移：在半夜做
  • 双写：所有写操作同时写入旧存储和新存储，后台异步迁移旧存储中双写前的历史数据到新存储，对比新旧存储的数据，修正不一致的数据

分布式事务

  • 分布式ID（订单ID）。比如“订单库写订单 + 库存库扣库存 + 用户库减余额”涉及到三个库，
  • 本地消息表 + 消息队列
    • 在一个 MySQL 单机事务里，同时完成两件事：创建订单+扣库存。一是往order表里面添加order，二是在msg_table里添加“扣库存消息”
    • 异步线程扫一遍msg_table，把消息都发给message queue
    • 消费者执行跨库操作。如果不成功，MQ会自动重试

Kafka

发表于： 2025-12-06 分类于： Tools

architecture

  • 同一个topic的partition不会跨cluster
  • 一个broker里面可能含有不同topic的partition
  • partition在存储上可以被看作为一个可追加的日志文件，每条消息加进去的时候带有一个offset
  • fault-tolerant: 多个节点故障时，集群仍能持续提供服务且数据不丢失。
    • 同一个partition会有多个replica,每个replica要么是leader（只有一个）, 要么是follower
    • 同一个broker里面不会有同一个partition的多个replica
    • 同一个broker里面会有同一个topic的不同的partition
  • 一群broker中有一个是controller,它不负责消息的传递，只负责选举partition的新leader
  • Zookeeper: 管理broker的状态

partiton

  • 高并发：多个producer可以向多个partition同时写入
  • Kafka 只保证在单个 Partition 内消息的顺序性
  • 高可用：多个replica

leader

  • 负责读写
  • Leader 负责管理 In-Sync Replicas（同步副本集）。它要确保 Follower 能跟上自己的进度，将落后的 Follower 踢出 ISR。
    • ISR：如果一个 Follower 在replica.lag.time.max.ms时间内没有发送pull request,它就会被踢出ISR
    • ISR存放在zookeeper中，controller broker会查看ISR中的信息，以方便知道每个partition的follwer是否跟上了它们的leader

follower

定期向leader发送pull请求

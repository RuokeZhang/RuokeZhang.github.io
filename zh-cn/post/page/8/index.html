nums = [10,9,2,5,3,7,101,18]
import bisect
def sol(nums):
    g=[]
    g_idx=[]
    n=len(nums)
    parent=[-1]*n #记录nums[i]在最终答案里的上一个数字的index
    for i, x in enumerate(nums):
        idx=bisect.bisect_left(g, x)
        if idx>0:
            # its has a preceding number
            parent[i]=g_idx[idx-1]
        if idx<len(g):
            g[idx]=x
            g_idx[idx]=i
        else:
            g.append(x)
            g_idx.append(i)
    cur_idx=g_idx[-1]
    res=[]
    while cur_idx!=-1:
        res.append(nums[cur_idx])
        cur_idx=parent[cur_idx]
    return res[::-1]

消息可靠性

生产者->MQ

  • 生产者开启 confirm 模式

if (!channel.waitForConfirms(5000)) {

  • 异步确认：发送消息后不阻塞等待 MQ 的 ACK，而是通过回调函数接收 ACK 通知；若回调中发现未确认（如 ACK 失败、超时），将未确认的消息存入本地缓存，定期触发重试，直到收到 ACK 或达到最大重试次数；
  • 同步确认：发送消息后阻塞等待 ACK

MQ

  1. 持久化（必做）：设置消息和队列为「持久化模式」（RocketMQ 默认开启），MQ 会将消息和队列信息写入磁盘，即使 MQ 进程宕机、重启，也能从磁盘恢复消息，避免内存中的消息丢失；
  2. 集群多副本（进阶，提升可靠性）：搭建 RocketMQ 集群，配置多副本（类似镜像队列），将队列数据同步到集群多个节点，设置节点同步模式（如同步复制）；

MQ->消费者

  1. 手动 ACK
    • 自动 ACK 的确定：会存在消费者收到，确认之后没消费，消费者挂了，数据丢失
  2. 死信队列： 当消息多次重试（如3次）仍处理失败（如系统异常），将消息转入「死信队列」，由人工介入排查处理，避免消息无限重试或被丢弃

幂等性

为什么会有重复的消息

  1. 生产者没收到 MQ 的 ACK，又发了一次
  2. MQ 没收到消费者的 ACK，又发了一次

解决

  • 数据库唯一索引
  • Redis SETNX /Lua 脚本查状态改状态

对比Kafka的优势

  1. Consumer 端自带重试机制，当消费消息失败时，RocketMQ 会自动将消息放入重试队列。
  2. 当消费消息失败时，RocketMQ 会自动将消息放入重试队列

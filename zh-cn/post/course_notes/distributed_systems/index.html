Semantics

At most once

  • have reply, the server恰好执行了一次
  • have no reply, server执行了一次/零次

At least once

  • have reply, the server至少执行了一次
  • have no reply, server执行了零次/一次/多次
  • 对read-only的operation来说，没问题。或者对幂等的操作也没问题，比如MapReduce中的Map阶段

primary backup

CAP

  • Consistent views of the data at each node
  • Availability of the data at each node
  • Tolerance to network partitions

BASE

  • Basically Available (基本可用): 系统保证能用，但可能偶尔失败或响应慢一点。

  • Soft state (软状态): 数据状态可能会在没有外部输入的情况下发生变化（因为数据正在节点间同步）。

  • Eventual consistency (最终一致性): 系统不保证你读到的立刻是最新的，但保证“过一会儿”所有节点的数据会达成一致。

正常运行流程

Client 发送：客户端只把请求（如 Put）发给 Primary 。

Primary 定序：Primary 收到请求，决定执行顺序（比如先 A 后 B）。

转发 (Forward)：Primary 把操作转发给 Backup 。

Backup 执行：Backup 收到后，执行操作（或记录日志），确保自己状态跟上了 Primary，然后回复 Primary“我好了” 。

Primary 执行并回复：只有收到 Backup 的确认后，Primary 才能执行并回复 Client“成功”

view server

ViewServer维护当前的View
一个View的组成：

  • ViewNum
  • Primary
  • Backup

所有服务器定期给 ViewServer 发 Ping(ViewNum)。如果 ViewServer 发现 Primary 没动静了，就宣布一个新的 View，提拔 Backup 做新的 Primary

state machine replication

$$\text{相同的初始状态} + \text{相同的输入指令} + \text{相同的执行顺序} = \text{相同的最终状态}$$

故障恢复

  1. view server发现某个server没动静了，于是创建新的view. 并且在之后的ViewReply中把这个新 View 告诉它们
  2. 当server收到ViewReply，发现自己是Primary，并且backup节点有更新的时候，它会做这些
    • State Transfer: 把内存中所有k-v打包，发RPC给新的backup
    • Wait for Ack: 在收到新的backup的回复之前，Primary不能处理client的任何请求
    • 只有在收到新backup的回复之后，Primary才会在Ping中使用刚才从view server处收到的viewNum,代表现在的primary/backup结构已经完全和view server刚才指定的一致了
  3. 假设这一切的背景是：client 给Primary A 发请求，却timeout了，于是client找到view server, view server返回一个完整的view. 那么client 就去请求新的Primary

make sure the requests are only executed on the current view.

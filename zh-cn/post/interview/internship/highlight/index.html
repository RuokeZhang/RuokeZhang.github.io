Candidate Part

  • First, we aggregate the livestream into minute-level metrics, including normalized signals like watch PV, user actions, and order creation.
  • Then, instead of using a single metric, we combine them into a composite score and apply a 5-minute rolling z-score to detect spikes relative to the recent baseline. This helps us identify highlight moments in a way that adapts to different livestream dynamics.
  • for each peak, we calulate a contribution score, means how much a metric contribute to the composite score, and assign a tag to a peak. for example, a peak may have “engagement-driven” or “conversion drivien” tag
  • For each peak, we verify whether the previous minute shows a similar pattern,
  • Finally, we expand each detected peak into a candidate window. The expansion strategy depends on the tag—for example, traffic-driven highlights require more context, so we expand further, while conversion-driven highlights tend to be more localized.

segment_edit_prompt INFO:
1. 输入信息：
    ◦ 候选片段（可能用于高光视频的 transcript 片段）；
    ◦ 产品列表（直播中销售的产品清单，按序号 1、2、3... 排列）；
    ◦ 完整直播 transcript（供上下文参考）。

• 识别主产品：从候选片段中确定 1 个最核心的产品，需与产品列表中的某一项精准匹配；
• 验证片段有效性：确保片段包含该产品的清晰实物演示（如功能、用法、特点），且不包含无关信息；
• 编辑片段：删除与主产品无关的内容（如其他产品、价格、直播互动话术等），生成连贯的独立演示脚本。

1. 输出格式：包含 5 个字段：
    ◦ reasoning：解释主产品的确定依据及片段有效性的理由；
    ◦ edited_excerpt：编辑后的片段（含 ||| 标记）；
    ◦ num_products：编辑后片段中涉及的产品数量（只能是 1 或 0）；
    ◦ product_index：主产品在列表中的序号（如 “3”，无效时为 “-1”）；
    ◦ is_valid：片段是否适合作为独立产品演示（True 或 False）。

ROUND 3: critique

分别给ChatGPT和Gemini发送：segment_text, edited_excerpt, main_product

  1. 产品展示（PRODUCT DEMONSTRATION）片段需清晰呈现主产品的物理属性（如外观、材质）、功能（如操作方式）、价值 / 好处（如使用体验），包括主播的个人使用感受或直接展示产品的对话（例如 “你看这个面料摸起来很柔软”“按这个按钮就能启动”）。

  2. 焦点清晰度（FOCUS CLARITY）片段必须仅围绕主产品展开，不能提及其他产品，也不能存在 “多个产品混杂、主次不分” 的模糊性。

  3. 内容相关性（CONTENT RELEVANCE）只保留与主产品展示相关的信息，必须删除：

    • 价格、促销、折扣；
    • 直播特有话术（如 “点击链接”“关注直播间”）；
    • 观众互动（如 “有人问尺码”）；
    • 其他产品的提及。

  4. 时效性（EVERGREEN POTENTIAL）避免时间敏感信息（如 “618 特价”“今天仅限 50 单”“7 月 1 日前发货”），但允许与季节 / 天气相关的描述（如 “冬天穿很保暖”“防雨材质适合雨季”）。

  5. 真实性（AUTHENTICITY）严格保留原始 transcript 的用词、拼写、语法、标点和大小写，不能擅自改写、修正或 paraphrase（意译）。

ROUND 4: refine

input: segment_text, edited_excerpt, main_product, gpt_critique, gemini_critique

二、核心约束（Important）这是优化的 “红线”，确保片段的真实性和合规性： • 严格保留原始内容：必须原样保留 transcript 中的用词、拼写、语法、标点和大小写，不能改写、修正或意译（paraphrase）。 • 仅能删除或复制：优化只能通过两种操作实现：1. 删除初步编辑片段中的冗余内容；2. 从原始 transcript 中复制未被初步编辑包含的相关内容（原样添加，不做任何修改）。绝对禁止添加、推断 transcript 中没有的信息。

三、编辑规则（Editing Rules and Conventions）具体规定了优化的操作细节，确保格式和内容合规：

  1. 删除标记：用 ||| 标记删除内容的位置（例如 “这个杯子 ||| 很耐用” 表示中间内容被删除）。
  2. 禁止修改原始文本：保留的任何文字必须与 transcript 完全一致（包括错别字、语法错误等）。
  3. 内容筛选：只保留与主产品 “实物演示” 直接相关的内容，删除：- 其他产品提及；- 直播特有话术（如 “点击下方链接”）；- 价格、促销信息；- 观众互动（如 “有人问尺码”）；- 模糊或重复内容。
  4. 片段长度：每个保留的连续片段至少 5 个词（避免过短导致语义不完整）。
  5. 整体要求：优化后的片段需连贯、聚焦主产品，可作为独立的产品演示视频脚本；若无法满足（如信息不足、焦点模糊），返回 null。

ROUND 5: evaluate

input: candidate_segment, binded_products, final_excerpt, product_name

输入final_excerpt，让大模型打分，分数为1-5分。不超过某个阈值的segment被视为不优秀的片段

  1. Product Identification: Is the main product explicitly named or described in the excerpt, matching the provided main product field? Do not infer or assume—accept only what is stated.

  2. Ambiguity Check: Could the excerpt refer to more than one product in the product list? If so, note this ambiguity.

  3. Claim Verification: Are all product features, names, and descriptions in the excerpt directly supported by the transcript and main product? Avoid any fabricated or unsupported claims.

  4. Excerpt Quality: Is the excerpt suitable as a standalone product video clip? Confirm that:

  • All irrelevant content is removed and separated by ||| as instructed.
  • Each segment is at least 5 words long.
  • Each segment ends smoothly and naturally, not cutting off mid-sentence or mid-thought before the ||| separator.
  • The excerpt is coherent and understandable on its own.

系统运行流程

轮询器（Poller）

  • 我们的服务定期去查询 “是否有新的直播结束事件”，用SET NX尝试获取全局游标锁（存上次查到的最新直播结束时间），然后从Redis拿到这个全局游标的timestamp.
    • SET poller_cursor_lock instance_A EX 10 NX
    • 10秒过期
  • 将“生成任务”写入 Redis 延迟队列（score = 直播结束时间+5min，表示可立即执行， ZSET实现）
  • SET 全局游标为此次直播结束的timestamp
  • lua脚本先检查锁的value是不是自己的， 如果是，就释放锁

Worker（分布式）循环

  • 核心逻辑：不断从延迟队列中获取“到期”任务（score ≤ now），处理流程如下：

  • Worker 抢到任务后，给这个任务加分布式锁（SETNX + UUID + TTL），超时时间30分钟

    • 必须在整个任务完全执行成功之后，才用 Lua 脚本释放（先判断是不是自己的锁，才能释放）
    • 如果任务失败、中断、超时，不主动释放，让锁自动过期，配合看门狗续期，防止并发重复执行。同时启动一个后台线程作为 “看门狗”。这个线程会每隔一段时间（超时时间的 1/3) 检查当前任务是否还在执行，如果任务没执行完，就自动把锁的超时时间重新设置为 30 分钟

token bucket

  • 在每轮调用之前，worker 调用 Redis Lua 全局 token-bucket 脚本尝试扣 tokens：

  • 扣成功 → 直接调用模型；

  • 扣不下 → 计算 wait_ms 或 backoff

    • Backoff with Jitter: 第一次重试等 2 秒 ±1 秒，第二次等 4 秒 ±2 秒，分散重试流量

  • 五轮调用大概在25000 token, 大促期间平均一天1.3万场, qps=1, 然后平均每天10000美金

  • global token桶

    • capacity: 10000
    • rate: 50000/60=8333（假设TPM为50000）

剪视频

RocketMQ

  • 传call_back_uri: RocketMQ 的oec_dms_live_highlight_generation/web_common 主题
  • 集群消费：给消费者组配置了集群消费模式。RocketMQ在发消息的时候，按顺序依次发给不同的消费者(go instance). 但是网络波动/重启都会导致同一条消息被消费多次
  • 消费回调函数：查 Redis 状态→更新为done,发送 ACK

Redis

  • cache_key: room_id+uuid
  • cache_value: 商品信息， status
  • 收到剪辑完成的任务之后， 用 Lua 脚本把 “查询当前状态 + 更新状态” 做成一个原子操作，然后发送 ACK

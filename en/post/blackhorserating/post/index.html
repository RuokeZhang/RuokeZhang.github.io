Like Design

Use Redis sorted set: key is post ID, set stores user IDs who liked, score is timestamp of like.

When frontend views post details, backend needs to:

  1. Fetch content from database by post ID
  2. Check Redis to determine if current user liked this post
  3. Add liked field to Blog object and return to frontend

Frontend doesn’t send current like status; backend checks if user liked by checking sorted set for user ID.

Then update like count in post database and Redis sorted set.

  1. Hot/cold data separation
  • When user likes, write to Redis ZSET first
  • Background async task periodically syncs to MySQL (avoids high-frequency write pressure)
  1. Data sharding
  • Time-based sharding: Create sub-keys by day/week (e.g., post:123:likes:20231001)
  • Pros: Naturally supports time range queries
  • Cons: Cold data needs regular cleanup

Feed Stream

When someone posts, save content to database and push to followers’ inboxes. Inbox sorted by timestamp (newest to oldest).

Feed data constantly updates - newest post index is 0, so all post indexes change. Traditional pagination doesn’t work.

Design inbox with sorted set. When reading, record timestamp of oldest post read (A). Paginated queries only fetch posts older than this timestamp.

If multiple posts have same timestamp A, handle in subsequent paginated queries.

  1. First request: frontend gets timestamp, offset initialized to 0. Return minimum timestamp found.
  2. Subsequent requests: pass timestamp returned from first request.
